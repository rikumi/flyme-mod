# 应用导航栏取色

功能仍仅在 SystemUI 内运行，沿用应用选择、任务子图层、排除补色层采样和最近任务缓存。无需注入目标应用。

## ColorOS 原生路径核对

依据 OPPO PKT110 对应 SurfaceFlinger 二进制以及 `ViewRootImplExtImpl`，并非通过最终屏幕截图统计多数颜色。

- SurfaceFlinger `0x5bf8d0–0x5bf9a8`：构造左边缘、中央、右边缘的排除区域，再由完整采样矩形减去该区域，留下左右窄带。其横坐标可写成 `[L + offsetX, L + offsetX + sideWidth)` 与 `[R - offsetX - sideWidth, R - offsetX)`。后续还有图层区域变换、相交和可见性处理。
- `0x5c1f50–0x5c1f9c`：将保存的 Region 换算到捕获缓冲区坐标，再与可用矩形相交。
- `Variance::pick`，`0x5c9a30–0x5c9bec`：先以 sideVarianceLimit 检查 Region；失败时改用矩形底部横带和 lineVarianceLimit，默认横带厚度为 3 个缓冲区像素。
- `0x5c9e18–0x5c9e78`：将 RGB 三通道方差取平均，与阈值比较；通过后返回平均颜色，而非颜色占比最高的像素。
- `ViewRootImplExtImpl.initDecorNavBarBgColor()`：首次采色之前用窗口原有的不透明导航栏颜色初始化。

因此中央灰色占据多数宽度、但两侧仍为白色时，左右采样区域可直接得到白色。这里不需要识别“灰色前景”的语义，也不能恢复被完全不透明像素遮住的颜色。

## Flyme 独立实现

Flyme 参考 framework 未提供 ColorOS 的 `OnColorPickedListener` 原生引擎，因此使用现有任务截图架构独立计算，不能声称完整复刻闭源引擎。

- 取导航栏上方最多 10 行，避开补色层覆盖的 1 像素接缝；无需对导航栏内部做完全相等检查。
- 优先联合统计左右两条窄带，分别向内偏移 2 像素、宽最多 8 像素；左右一起计算方差，防止两侧异色时任选一侧或混出无依据的新颜色。
- 两侧失败后，统计捕获区域底部 3 行整宽横带。
- RGB 平均通道方差阈值分别为 100 和 25；这些阈值参考 ColorOS，而 10/2/8 的采样几何是本实现的参数，并非已确认的 ColorOS 默认值。
- 透明采样或两级均失败时不提供补色，沿用原来的撤去补色行为；没有加入未经核对的历史颜色保留机制。
- 关闭开关、应用切换、任务失效与最近任务行为仍由已有生命周期管理。

## 验证

`tests/navigation-sampling/NavigationSamplingTest.java` 可直接与两个采样类一起用 JDK 21 编译运行。覆盖中央 97% 灰色而两侧白色、两侧异色、横带后备、透明区域、低幅噪声、高方差、阈值边界、小尺寸与接缝排除。

纯算法检查和 APK 构建不能代替 Flyme 设备上的显示确认。特别需要验证两侧白边窄于采样带、圆角透明像素、页面动画、最近任务进入退出和关闭开关的恢复。
